🟨 **Story:** As the maintainer of claude-bdd, I want every behaviour example in `features/*.feature` to be checked automatically, so that a change to a SKILL.md that breaks a confirmed rule is caught before release.

Markers: `✓` confirmed by you · `!` Claude is sure, with evidence · `?` Claude's guess · `⚠` suspected problem.

Background (research, 2026-10-13): `claude plugin eval` runs each case as a fresh `claude -p` with only this plugin loaded, 3 runs per case by default. A case is `evals/<dir>/case.yaml` (or `prompt.md`) plus graders: `regex`, `file_exists`, `tool_used`, `tool_order`, `llm` (judge, 2 of 3 votes). A bash `scaffold_script` seeds the empty workspace (needs `--scaffold`). Exit 0 = all cases pass. Source: code.claude.com/docs/en/plugin-evals.md

## Which examples get what

### R1 ✓ Examples about Claude's behaviour (discover, formulate, automate) become `claude plugin eval` cases. Examples about files in this repo become pytest tests
Evidence: eval graders see the reply, the transcript and created files; they cannot run Python asserts. pytest cannot judge a model's reply.
- B1.1 The one where formulate must stop at an open `?` (B31.1) → eval case
- B1.2 The one where the README must have the install block near the top (B7.1) → pytest test reading README.md

- ⚠ B2.1 in the feature ("repo is English") has no sensible automatic check → see F1

## How a case is built

### R5 ✓ State that an example assumes ("Given R4 is still marked ?") is written by the case's `scaffold.sh` into the empty workspace; the "When" is the prompt; the "Then" lines become graders
Evidence: `scaffold_script` is the documented way to seed files; `file_exists` and `target: {source: file}` grade files the skill wrote.
- B5.1 The one for B31.1 → scaffold writes a scratchpad with R4 marked `?`; prompt "/bdd:formulate"; graders: reply names R4 (regex), no `*.feature` created (file_exists false), judge confirms it stopped

### R6 ✓ Deterministic graders first (regex, file_exists, tool_used); an `llm` judge only for what no pattern can check
- B6.1 The one for B25.1 → regex `Scratchpad in German or English\?` with `count:1`, no judge needed

### R7 ✓ Skills ask the user in plain text in their reply, not through the AskUserQuestion tool
- B7.1 The one for B51.3 → the reply contains "Install pytest-bdd?" and the run ends there
- ⚠ AskUserQuestion's behaviour in unattended eval runs is not documented; plain text is gradable with regex. Downside: no clickable answers in the app → see F2

### R8 ✓ Examples that need an earlier turn (B24.2 "already suggested in this conversation") use `context.history_file` with a hand-written transcript. If that turns out to be impractical, the example is checked by review and listed as such
- B8.1 The one for B24.2 → history file contains one earlier suggestion; graders: regex `example map` with `not_contains`

## Running them

### R9 ✓ Evals run with `--ablation none` by default (no baseline run without the plugin), which halves the cost
Evidence: the baseline arm doubles every case; it measures "plugin vs no plugin", which we only need once for the README, not on every change.

### R10 ✓ Two run levels: a quick run (`--runs 1`, one model) during development, and a full run (`--runs 3`) before every release, with `--max-cost-usd` as a ceiling on both
- B10.1 The one where a SKILL.md changes → quick run of that skill's cases (`--tag discover`)
- B10.2 The one before tagging v0.2.0 → full run of all cases
- ⚠ rough cost guess: ~55 cases × 3 runs ≈ 165 model runs plus judge calls; unknown until the first measured run → see F3

### R11 ✓ Evals run locally, not in GitHub CI: they need a Claude login or API key and cost money per run. CI runs only pytest
- B11.1 The one where someone opens a pull request → CI runs pytest and the coverage script, not evals

### R12 ✓ The decisions above are written down in `evals/README.md` (how to run, how to add a case), not in a `.feature`, because they describe how this repo tests itself, not what the plugin does
Evidence: R6/R36 put plugin behaviour in `features/`; this scratchpad is maintainer tooling.

### R13 ✓ (from the gaps round) PLAIN-mode evals of automate do not check runner bindings. A seeded project with its own test suite goes in; an `llm` judge checks two things in the written tests: (a) each test asserts exactly its example's Then, (b) the tests blend into the existing suite (same framework, folder, naming, fixtures and helpers as the neighbouring tests)
- B13.1 The one for B58.1 → scaffold seeds a small pytest suite with a house style; graders: the new test files mention `<slug>:<ID>` (regex), the judge scores intent and blend-in
